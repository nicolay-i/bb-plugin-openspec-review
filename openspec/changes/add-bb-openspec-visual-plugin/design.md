## Context

Мотивация и поведение описаны в proposal.md и трёх delta specs. Это новый отдельный репозиторий внутри общего checkout; исходники других проектов не входят в его Git-историю.

Исследован официальный https://github.com/Fission-AI/OpenSpec на main `6d04a1b`; установлен CLI 1.9.0. В исследованном main есть `list --archived` и `status --all`, отсутствующие в установленной версии. Не строить реализацию на непроверенных командах main.

Doc Review находится в https://github.com/xMinor-1/bb-plugins/tree/main/plugins/doc-review, лицензия MIT, Copyright (c) 2026 Foma. Его Markdown-ревью уже содержит выбор текста, комментарии, диалоги и передачу агенту; универсальный просмотрщик связан с PDF/Office/HTML. Копировать следует нужный исполняемый путь, не весь плагин с последующим отключением форматов. Перед переносом зафиксировать точный upstream SHA.

## Goals / Non-Goals

**Goals:**
- Минимальная самостоятельная адаптация Markdown-ревью внутри визуального OpenSpec-навигатора.
- Один путь чтения данных, явная диагностика ошибок, изоляция хостов и окружений.
- Сохранение истории без изменений исходных OpenSpec-документов и метаданных; независимость архива OpenSpec от lifecycle чатов.

**Non-Goals:**
- Собственный OpenSpec-движок, AI-сервис, произвольный редактор Markdown или управление lifecycle изменений.
- Общая библиотека для двух плагинов, импорт базы Doc Review, PDF/Office/HTML, рисунки и PDF-экспорт.
- Stores, глобальные defaultStore и перенос обсуждений между worktree в первом релизе.
- Определение текущего Propose по тексту переписки, имени файла или статусу активности треда.

## Decisions

### 1. Самостоятельный пакет, только публичный BB SDK

Основной frontend — правая панель треда; отдельный navPanel с выбором проекта/окружения — дополнительный обзор. Собственные документы открываются внутри плагина; глобальный fileOpener для `.md` не регистрируется. Переходы используют host-owned navigation/panels, рендеринг Markdown и компоненты BB. В правой панели всегда один рабочий столбец: список → документ → назад, без пустой колонки Documents. Технический root/host и пояснения свёрнуты в раскрываемый блок контекста. На отдельной странице два столбца допускаются только при выбранном документе и достаточной ширине самого контейнера, через CSS container queries, а не viewport-breakpoints окна BB. Комментарии доступны под документом, без обязательной третьей колонки.

Backend: типизированный RPC, SQLite для обсуждений и небольшое KV/metadata-хранилище выбора. Host entry: выполнение CLI, чтение файлов, нативные watches. Никаких private `@bb/*` импортов или патчей ядра.

Альтернатива — обязательная интеграция с отдельным Doc Review — отклонена: нужен цельный интерфейс и контроль идентичности обсуждений. Выделение общей библиотеки сейчас добавляет второй релизный контракт без необходимости.

### 2. Repo-local контекст и один контракт OpenSpec

Контекст задаётся проектом, окружением и хостом, которые backend разрешает через BB SDK. На хосте определить ближайший repo-local OpenSpec в пределах checkout; не позволять случайно выбрать корень соседнего проекта или глобальный store. На каждом действии проверять принадлежность разрешённому контексту. Если CLI разрешил иной корень, остановить операцию.

Целевой базовый контракт — OpenSpec 1.9.0: `list --json`, `list --specs --json`, `status --change <id> --json`, `instructions apply --change <id> --json` для данных задач. Перед фиксацией поддерживаемого диапазона проверить эти ответы на тестовом корне и объявить минимальную проверенную версию. Новые версии разрешать только при успешной проверке обязательных полей, не угадывать изменившийся контракт.

Архив перечислять напрямую из `openspec/changes/archive/`, документы читать с хоста; это единственный штатный путь архива в v1, не fallback после неуспешного CLI. Архив показывать как сохранённые документы и задачи без выдуманного актуального графа их старой схемы. Активный граф брать из `status`; нестандартные артефакты и glob-пути брать из ответа, а не из четырёх зашитых имён. Не загружать status каждого изменения при каждом рендере списка: список даёт краткий прогресс, подробности запрашиваются по выбору.

CLI запускать с аргументами без shell-интерполяции, фиксированным cwd, timeout, лимитом вывода и отключённой телеметрией для вызовов плагина. Обрабатывать stdout JSON и stderr отдельно; код ошибки не превращать в успех. Проверять exit code и схему ответа.

Альтернативы — импорт внутренних модулей OpenSpec, собственный Markdown-парсер всего workflow и поддержка двух веток CLI — отклонены как дополнительные контракты.

### 3. Данные UI и обновление

Навигатор содержит три раздела: действующие спецификации, активные изменения, архив. Поиск v1 — по имени/пути, без полнотекстового индекса. В карточке отдельно показываются существование/готовность документов и выполненные задачи. Без задач — «задачи не заданы», а не 100%. Валидация и фактическая реализация не выводятся из наличия файлов.

Связи многие-ко-многим хранить как набор `(threadId, context, itemKind, itemId)` с уникальностью каждой пары. Item — действующая спецификация или изменение; один тред может иметь несколько связей, один item — несколько тредов. Показывать связи в панели треда и карточке item. Выбор открытого документа — отдельное UI-состояние, не замена связей. При исчезновении/архивации исходного item показать его отсутствие, не перепривязывать автоматически. Связь — явная пользовательская привязка, не индикатор выполняющегося workflow.

Использовать host watches для инвалидации и ограниченное обновление видимых данных не чаще одного запроса в 4 секунды; не держать параллельные refresh одного контекста. После reconnect перечитать состояние. На смене контекста отменить запросы и игнорировать запоздавшие ответы. Последний успешный снимок при ошибке явно помечать устаревшим. Watches/таймеры освобождать при закрытии, disable и reload.

### 4. Адаптация Markdown-review

Перенести минимальную связку Markdown renderer/selection, comment list/editor, хранилище комментариев/ответов и построение handoff-сообщения. Удалить зависимости и ветки, нужные только PDF, Office, HTML, browser automation и экспорту. Использовать отдельные command names и skill, например `bb openspec review list|show|reply|resolve`; окончательный manifest id проверить на конфликт при scaffold.

Отправка v1 — только в выбранный существующий тред того же окружения, с явным подтверждением и queued delivery. Ни автоматического создания тредов, ни запуска OpenSpec workflow. Передавать путь, root/host/environment, цитату, идентификатор и историю замечания. Отмечать отправленное только после подтверждения BB; неопределённый результат доставки показывать пользователю без автоматического повтора. Resolve означает отчёт агента о выполнении замечания, а не проверку реализации плагином.

Сервер ограничивает размер текста, списка замечаний и ответов. Не переносить инструкции из документов в системные инструкции агента. Markdown рендерится безопасным host renderer без исполнения raw HTML. Повторно использовать существующие тесты только для оставленной функциональности.

### 5. Идентичность документа и независимые архивы

Хранить собственный неизменный documentId и locator `(hostId, checkout/root, relativePath)`. Комментарии и ответы ссылаются на documentId. Для текущей версии хранить цитату, контекст и координаты; пропавшая либо неоднозначная цитата помечается как непривязанная, история не удаляется.

Архивирует только штатный OpenSpec. В v1 нет ни автоматического переноса обсуждений, ни ручного сопоставления с архивом, ни общей операции архивации спеки и чатов. Архивный документ — отдельный объект; прежняя история остаётся доступной у исходного documentId с отметкой отсутствующего файла. После обнаруженного исчезновения освободить locator для новой генерации документа при повторном появлении старого пути, не отдавая ей прежние комментарии. Не обещать обнаружение удаления и восстановления целиком между наблюдениями.

Не внедрять UUID в `.openspec.yaml` и не переписывать исходные спеки ради ревью. Обсуждение delta spec не переносится на живой spec при merge. Архивация/закрытие BB-чата не вызывает изменений OpenSpec; архивирование OpenSpec не вызывает lifecycle-операций BB-тредов. Несколько чатов могут работать с одной спекой и наоборот.

### 6. Локализация и распространение

Два полных словаря EN/RU без тяжёлой i18n-зависимости. Явная настройка языка, начальное значение EN, одинаковый набор ключей проверяется тестом. Внешняя диагностика сохраняется как исходная подробность рядом с локализованным пояснением; содержимое документов не переводится.

README и package description на английском. При переносе кода сохранить MIT-текст/авторство и добавить документ о происхождении с upstream SHA и перечнем адаптированных частей. Собственный лицензионный выбор и аккаунт GitHub подтвердить перед публикацией; ничего не публиковать в ходе планирования. Репозиторий включает planning artifacts, но не базы, секреты и исследовательские копии.

## Risks / Trade-offs

- Универсальный Doc Review тесно связан с другими форматами → перед основным переносом небольшой extraction spike; если удаление форматов требует изменения архитектуры, остановиться и обсудить, не копировать весь viewer скрыто.
- CLI 1.9.0 и main различаются → проверить ровно используемый JSON-контракт; не обращаться к неопубликованным флагам.
- История не следует за перемещением в архив → явно показывать отсутствие исходного файла и сохранять историю; не добавлять новый архивный workflow.
- Worktree с одинаковыми файлами имеют разные обсуждения → прямо документировать границу v1, не объединять похожие документы.
- Симлинки и путь от клиента могут вывести за root → канонизация realpath, проверка границ на хосте, повторная проверка при чтении.
- Метаданные/watch могут не обнаружить намеренно восстановленные timestamps → ручное принудительное перечитывание документов; не заявлять криптографическое доказательство свежести.

## Migration Plan

1. В этом подрепо создать пакет через штатный scaffold BB и зафиксировать совместимые SDK/CLI.
2. Перенести только Markdown-review с MIT provenance, реализовать навигатор и проверки границ.
3. Проверить локальный и удалённый хост, совместную установку Doc Review, desktop/web и узкий экран.
4. Установить локально под отдельным plugin id; проверить сохранность обсуждений после reload/disable/enable.
5. После согласования GitHub и лицензии опубликовать готовый репозиторий, проверить clean Git install по README.

Миграции базы — только append-only. Удаление плагина может удалить его обсуждения по обычным правилам BB, что должно быть указано в README. Откат установки — отключение плагина без изменений OpenSpec-файлов; не обещать обратную совместимость неизвестных будущих миграций.
